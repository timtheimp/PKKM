# PKKM — Kingmaker Kingdom Manager (initial native Windows release)

[![PKKM CI](https://github.com/timtheimp/PKKM/actions/workflows/ci.yml/badge.svg)](https://github.com/timtheimp/PKKM/actions/workflows/ci.yml)

Contribution and workbook-safety guidance is in [`CONTRIBUTING.md`](CONTRIBUTING.md).

PKKM is released under the [MIT License](LICENSE).

PKKM is a local-first C++17 Win32 desktop application for kingdom management. Its framework-independent domain library calculates the currently implemented stat, alignment, law/edict, leadership, Control DC, population, and settlement aggregation rules. Kingdom data is versioned UTF-8 JSON schema v10; schemas v1-v9 migrate forward with their established defaults, while schema v10 persists Greenbelt image metadata, calibration, axial hex state, claim state, linked settlement IDs, and improvement IDs. If settlement records exist, their count and stat totals feed the kingdom summary; population and districts derive from catalog lots and stored overrides, while legacy territory aggregates remain the fallback when there are no settlement records. The CLI and desktop dashboard show signed stat modifier breakdowns and settlement totals. The Win32 editor exposes kingdom, statistic, law, and leadership inputs. **Manage Settlements** edits settlement fields, catalog-backed inventory, and a per-settlement checkbox for applying catalog Economy/Loyalty/Stability bonuses to kingdom totals. The checkbox is off by default, and saved settlement totals are preserved; Defense/Unrest remain preview-only and costs are not yet applied. **Greenbelt rule previews** expose the standard terrain-improvement catalog, including the source-specific 3pp Vineyard entry; **Kingdom Manager > Greenbelt Map** renders the bundled JPG, calibrated hex geometry, claimed-hex overlays, and the kingdom perimeter, while qualifying catalog applications update Greenbelt inventory automatically; BP spending, route costs, derived effects, and kingdom-stat changes remain manual, and unresolved prerequisites remain warnings or manual-only records. Schema v8 persists map grid dimensions, explicit zero-based rectangular building placements, visual labels as explicit non-overlapping regions, and manual checklist completion by turn; schema v9 adds calendar notes by source month occurrence; schema v10 adds Greenbelt state. Validation rejects invalid footprints, out-of-bounds items, and overlaps. Lot counts do not determine placement footprints. **Edit Map** provides a visual grid for 1×1 through 20×20, with inventory-backed or typed building names and terrain/corridor labels. Grid cells show label initials; full label text appears in the map-item list. Labels are descriptive only and have no terrain mechanics. Custom building names label placements only; they do not change inventory or catalog totals. **Load Template** offers optional `Capital Map`, `City # Map`, `Example Map`, and `Multi-District Map` layouts from the workbook. Replacing a populated draft requires confirmation, and the settlement changes only if the user selects **Apply**. The example's lot-count captions remain visual annotations, not general footprint rules. The source-defined terrain reference table is extractable with `tools/import_terrain_reference.py` into `assets/terrain_reference.json`; its values remain raw reference data and are not applied as hidden map mechanics. Qt is not installed, so the desktop shell uses Win32. This remains a partial migration rather than full workbook parity; XLSX import is available through the CLI importer and reports unsupported formulas explicitly. JSON parsing uses the vendored nlohmann/json 3.11.3 single header, so the C++ runtime has no external dependency.

## Build with Visual Studio Code
1. Install Visual Studio 2022/2026 C++ Desktop Development workload, Windows SDK, CMake, and the VS Code CMake Tools extension.
2. Open this folder in VS Code, run **CMake: Select a Kit**, choose a Visual Studio x64 kit, then **CMake: Configure** and **CMake: Build** (targets `pkkm_desktop` and `pkkm_tests`).
3. Run **CMake: Run Tests**. Launch `build/Release/pkkm_desktop.exe` for a Visual Studio multi-config kit, or the executable in the selected build configuration directory.

CLI alternative from a Visual Studio Developer Command Prompt:
```
cmake -S . -B build
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
python -m pip install openpyxl
python -m unittest discover -s tests -p 'test_*.py'
```

Import a workbook copy into schema-v10 JSON and emit an auditable mapping report:

```text
python tools/import_workbook.py "C:/path/to/Kingdom of Template.xlsx" build/imported.json --report build/import-report.json --catalog assets/building_catalog.json
```

The importer maps direct kingdom, law, leadership, settlement, inventory, workbook-map, and Calendar note inputs. It does not evaluate spreadsheet formulas; every formula cell is listed in the report, along with manual workflow and reference-sheet limitations. The source workbook is never written, and the CLI rejects any output path that resolves to the source workbook.

Export a schema-v10 JSON file to a new multi-sheet XLSX report without modifying the JSON source:

```text
python tools/export_workbook.py build/imported.json build/exported.xlsx
```

The exporter creates Kingdom, Rules, Settlements, Buildings, Placements, Greenbelt, Events, Construction, Valuable Sales, Calendar, and Turn Actions sheets. Nested values are retained as JSON text where a single spreadsheet cell is required.

The native JSON save path also rejects `.xlsx`, `.xlsm`, and `.xls` destinations, preventing the desktop application from overwriting a spreadsheet source by mistake.

Create the portable Release archive with the repository script:

```text
python tools/package_release.py --build-dir build/Release --output build/deliverables/PKKM-current-schema10.zip
```

The script validates and archives exactly `pkkm_desktop.exe`, `pkkm.exe`, `building_catalog.json`, `Kingmaker-Greenbelt-Map.jpg`, and `random_magic_item_catalog.json`; temporary smoke fixtures and test binaries are excluded.

The normalized research catalog is generated with `python tools/normalize_random_magic_item_tables.py "R:/Obsidian/TheSilo/The Silo/Jarvis/PKKM - Random Magic Item Generation Tables.json" assets/random_magic_item_catalog.json`. It preserves the all-captured source profile, source URL, tier, lesser/greater variant, d100 range, item name, and price where supplied. `tools.normalize_random_magic_item_tables.resolve_category_result` resolves direct category tables and names source-defined deferred branches: spell selection remains manual for potions, scrolls, and wands, while categories with multiple body-slot or equivalent subtables remain manual until a subtable-selection rule is supplied. After configuring and building, run `cpack --config build/asset-copy-verify/CPackConfig.cmake -G ZIP -B build/deliverables`. The generated archive is named from the current project version, such as `PKKM-0.1.12-Windows.zip`, and contains the executables, catalog, and Greenbelt map asset; `tests/test_cpack_package.py` verifies the payload and rejects duplicates or test binaries.

The `pkkm` console target accepts `--help`/`help`, `--version`/`version`, `new <file.json>`, `show <file.json>`, `random-items <file.json> <seed>`, `random-items-apply <file.json> <seed>`, `random-items-availability <file.json> <base-value-gp> <seed>`, and `catalog <catalog.json> [query]`. `show` prints Control DC, population, settlement totals when present, catalog-derived lot/district/population values, and either applied catalog stat bonuses or a clearly labeled preview, followed by stat totals and check thresholds. `random-items` is a seeded, non-mutating settlement preview: it derives minor/medium/major slots from qualifying buildings, rolls one d100 category per currently previewed slot, records the selected all-captured d20PFSRD source profile, treats lesser/greater variants as internal variation rather than separate settlement tiers, applies an equal 50/50 lesser/greater variant chance, and reports the runtime catalog size. `random-items-apply` performs the explicit Upkeep mutation: it populates empty or previously sold slots, resolves direct source tables into generated stock, records manual-resolution states for spell-selection or multi-subtable branches, and saves the kingdom. `random-items-availability` is a seeded, non-mutating monthly availability preview: items at or below the supplied base value use the source 75% check, while items above it are reported as always available. `catalog` searches workbook-backed improvements by name, or lists all when no query is supplied. Example: `build/asset-copy-verify/Release/pkkm.exe catalog assets/building_catalog.json academy`. The native settlement manager also provides a non-mutating availability preview. Enter a base value in gp and a non-negative seed, then choose **Preview Availability**. The result reports available, unavailable, above-base-value, and manual-resolution slots without changing persisted stock. The native UI creates, opens, and saves JSON files and displays the calculated summary. The settlement manager displays persisted magic-item stock with tier, slot, state, item, and price; generated stock can be removed after confirmation, while manual-resolution stock remains visible and protected until its unresolved branch is handled. **Kingdom Manager > Calendar Notes** preserves the source template's 85 month occurrences in source order and exact literal year markers. It records freeform notes under Holiday, Kingdom Upgrades, Events, and Other. Apply commits the page changes in memory and leaves the tracker open; Cancel reverts edits since the last Apply; Close returns to the main window. **Kingdom Manager > Turn Checklist** tracks the 20 source procedure items, including optional items, independently by turn; it records completion only and does not calculate checks or outcomes. Apply commits the page changes in memory, Cancel reverts edits since the last Apply, and Close returns to the main window. The unresolved Stability failure-by-exactly-4 case remains manual. **Kingdom Manager > Manage Settlements** edits settlement records and inventory; Apply commits the page changes in memory, Cancel reverts edits since the last Apply, and Close returns to the main window. **Kingdom Manager > Edit Inputs** follows the same Apply/Cancel/Close workflow. **Edit Map** accepts inventory selections or typed building names, explicit footprints, visual labels, and grids through 20×20. A schema-v7 GUI smoke used a temporary 15×15 map with 14 labels and a Castle 2×2 placement: the map was applied, saved, reopened through **File > Open**, and inspected again in **Edit Map**; CLI read-back confirmed the labels and placement persisted. A separate template smoke loaded **Multi-District Map** over a populated draft, showed 14 labels and no building placement, then cancelled without saving. Grid cells show label initials, with full text in the map-item list. Save with a `.json` extension. Data is written to a temporary file and renamed into place. A sample starter file is at `examples/starter.json`.

The Turn Checklist is phase-ordered as Upkeep, Edicts, Income, and Events. Its guided **Complete Current Step** control advances through the exact source checklist order while keeping outcome entry manual, and optional steps require an explicit **Skip Optional Step** action; **Return to Previous Step** opens the prior resolved draft step for review without changing its current state. Guidance identifies the manual-resolution boundary for each step family, including settlement stock branches, map/claim decisions, construction facts, city placement, purchases, item transfers, and event rolls/consequences, and the guidance area wraps so the full instruction remains readable. The checklist window separates income, tax, event, handoff, guidance, navigation, summary, and Apply/Cancel/Close rows without overlap, has a `1010 x 940` minimum tracking size, and widens its long guidance/navigation/summary controls during `WM_SIZE`. All top-level project windows expose resize/minimize/maximize affordances; the custom improvement popup now does as well. **Open Turn Actions...** provides access to the existing supported action surface only after the checklist draft has been applied, preserving the Apply boundary. The guarded **Open Law Inputs...** handoff is available at `edicts.adjust_laws` after the checklist draft is applied. It opens the existing Edit Kingdom Inputs surface with laws, benefits, and leadership inputs available for caller editing; it does not infer law changes or mark the checklist step complete. The guarded **Open Army Worksheet...** handoff is available at `edicts.armies` after the checklist draft is applied. It records a source-faithful army roster and creation transaction from caller-supplied inputs, calculating soldiers, army CR, HP, DV, OM, morale, weekly Consumption, and explicit BP resource costs only. The worksheet also records caller-supplied mount CR, tactics, special abilities, prerequisites, and notes/GM approval as manual auditable fields. Leader details, tactics, prerequisites, special abilities, GM approval, and all battle outcomes remain manual; it never simulates combat or infers unsupported results. Apply/Cancel/Close remain explicit, and BP is spent only on modeled resource costs. Apply is still required to commit the checklist draft. The checklist also displays per-phase completion counts, including skipped optional steps. The first direct wizard adapter, **Apply Claim Hex (1)**, is available only when the applied workflow is at `edicts.claim_hexes`; it records the normal audited Claim Hex action, advances that checklist step, and preserves the explicit manual boundary that map selection remains caller-controlled. The guarded **Apply Withdrawal** adapter is available at `income.withdraw_gold`; it accepts caller-supplied BP amount and Loyalty-check result, records the normal withdrawal record, applies the documented Treasury/Unrest deltas, and advances the checklist step. The guarded **Apply Deposit** adapter is available at `income.deposit_gold`; it accepts caller-supplied gold and applies the existing exact `4,000 gp` unit rule before recording the deposit and advancing the checklist step. The guarded **Apply Item Deposit** adapter is available at `income.deposit_items`; it accepts caller-supplied item value, applies the active rule profile's exact conversion, records the profile-aware item deposit, and advances the checklist step. Item identity and inventory ownership remain manual because the existing record does not infer them. The compact guarded **Apply Taxes** adapter is available at `income.taxes`; it accepts Economy-check success, result input, and other BP inputs, applies the active profile's documented divisor, records the tax collection, and advances the checklist step. The guarded **Apply Event Roll** adapter is available at `events.roll_d100`; it accepts an explicit event-occurred flag and caller-supplied d100 roll, records the source-defined event kind and continuous status when an event occurred, and otherwise records only checklist completion. Event targets, checks, consequences, affected entities, and all unsupported outcomes remain manual. After the applied event-roll step is complete, **Open Event Resolution...** hands off to the existing Turn Actions event history and manual consequence controls without duplicating or bypassing that Apply boundary. When `edicts.build_improvements` is the current applied step, **Open Construction...** opens a settlement-manager construction context; the caller must select the settlement before opening the existing construction transaction editor. When `edicts.city` is current, **Open City Worksheet...** opens a settlement-manager city context; the caller must select the settlement before entering city-layout work. No settlement, building, terrain exception, district placement, or construction/city outcome is inferred. Turn Actions remains available as an advanced audit surface, and its recorded actions now display the corresponding checklist phase and step (for example, `Phase 2 Edicts / Step 2: Claim Hexes`). The domain exposes canonical turn checklist status, source-step mapping, explicit completion/skip mutation, and JSON round-trip coverage.

### Responsive native layouts

The Turn Checklist reflows its complete child-control set during `WM_SIZE`, preserving visual groups and reserving separate space for the Phase 3 income/withdrawal area and the bottom Apply/Cancel/Close band. The Greenbelt Map Editor keeps its tool panel docked to the right-side client boundary when resized or maximized. Turn Actions captures its complete baseline child layout, scales and repositions the controls as a group when the window grows, and retains the vertical scrollbar whenever the full action surface cannot fit. The Turn Actions default size is `900 x 850`, with a `760 x 650` minimum tracking size; normal and maximized native captures were verified, while direct corner-drag verification remains dependent on the desktop automation driver.


## Workbook source / coverage
The supplied template at `C:\Users\darks\Downloads\Kingdom of Template.xlsx` was read without modification. It contains Kingdom, Capital, Capital Map, Turn, City #, City # Map, Example Map, Multi-District Map, Calendar, and Data. The importer preserves source rows/cells and explicit row kinds; catalog search exposes only improvements. Regenerating the asset requires Python with `openpyxl`; the C++ runtime does not. Settlement records feed kingdom totals; catalog lots drive derived lots/districts/population, and opt-in catalog Economy/Loyalty/Stability bonuses affect kingdom totals while saved settlement totals remain intact. Schema v10 persists map dimensions, non-overlapping placements, visual labels, manual Turn checklist completion by turn, and Calendar Notes keyed to source month occurrences. The Win32 editor supports grids through 20×20 and optional presets for all four workbook map sheets plus the PDF City Layout 6×6 worksheet template. The PDF City Layout template is visual/manual only: it provides a blank six-by-six grid representing three two-by-two districts per side; it does not infer city rules, boundary Land/Water choices, item identity, or item generation. The adjacent PDF Worksheet editor records manual North/South/West/East Land/Water choices, base value, and four item-entry columns without generating inventory or applying city mechanics. The Calendar tracker preserves 85 source entries and three literal year markers without date arithmetic. Those map sheets define no terrain mechanics. The manual checklist does not automate outcomes.
